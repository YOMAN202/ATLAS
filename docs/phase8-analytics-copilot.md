# ATLAS
## Enterprise Supply Chain Intelligence Platform
### Phase 8 Proposal Review — Grounded Analytics Copilot

**Status: APPROVED IN PRINCIPLE, VERIFICATION-FIRST — 2026-08-14, NOT YET IMPLEMENTED**
*Scope: this document specifies an approved copilot design. Per explicit authorization, the verification harness (`docs/phase8-grounding-spec.md`) is the first implementation deliverable and a mandatory, CI-blocking release gate — the chat interface may not merge until it passes. No code has been written. Implementation of the harness itself awaits a separate, explicit go-ahead beyond this document.*

**Recommendation: approved, verification-first.** This proposal is architecturally distinct from, and materially more defensible than, the "LLM analytics copilot" and "natural-language dashboard querying" items rejected in `docs/final-architecture-review.md` §3. Those were evaluated as open-ended natural-language-to-SQL systems; this one is constrained to tool-calling over ATLAS's *existing*, already-audited, already-role-gated REST endpoints, with no new database credential, no SQL generation, and no path back into the write layer. Properly built, it never touches the deterministic analytical core — it sits strictly downstream of it. The original review of this proposal treated the verification harness as a precondition to sequence before the chat UI; the approved architecture goes further and makes it the literal first deliverable and a CI-blocking gate (full specification: `docs/phase8-grounding-spec.md`), closing the gap identified in that review — that a "build the harness first" ordering with no forcing function behind it is likely to erode in practice. Making it a blocking check, not a step in a roadmap, is the forcing function.

---

## 1. Why this is a different proposal, not a rebrand of the rejected one

`docs/final-architecture-review.md` rejected two related ideas:

- **LLM analytics copilot** — rejected as a general concept, on the grounds that an LLM in the query/narration path introduces non-determinism and hallucination risk "exactly where every other part of ATLAS was built to eliminate it."
- **Natural-language dashboard querying (NL-to-SQL)** — rejected specifically because arbitrary LLM-generated SQL against a real database is "a genuine new safety surface" that every other part of the platform deliberately avoids.

This proposal is not the same shape as either. The constraint that changes the analysis is explicit in the request: **"the copilot may query only through the analytics layer."** Read literally and enforced literally, that means the copilot never generates SQL and never receives a database credential — it calls the same FastAPI endpoints (`/api/v1/dashboards/...`) the Next.js frontend already calls, through the same `require_role` dependency, returning the same JSON the dashboards already render. The LLM's job shrinks from "write a correct, safe, minimally-scoped query against a real schema" (unbounded, genuinely dangerous) to "pick which of ~20 existing, already-safe, already-typed functions to call, and summarize what came back" (bounded, inspectable, and — critically — the same trust boundary the dashboard frontend already operates inside). That is a categorically smaller and different risk than open-ended NL-to-SQL, and it deserves its own verdict rather than inheriting the earlier one.

## 2. Architecture

```
User (role: supply_planner / executive / ...)
        │  natural-language question, X-Atlas-Role header (same as every dashboard)
        ▼
Copilot orchestrator (new, thin — no DB connection of its own)
        │
        ├─► Tool router: LLM selects 1+ tools from a FIXED, typed tool set
        │       Each tool = one existing dashboard endpoint, called in-process
        │       or via HTTP, with the SAME role dependency already enforced.
        │       Examples: get_forecast_summary(), get_supplier_risk_detail(...),
        │       get_scenario_compare(ids), get_service_level_detail(product_key),
        │       get_inventory_policy_detail(balancing_recommendation)
        │
        ├─► Each tool result carries a citation block, assembled by CODE,
        │       not generated by the LLM: {source_table(s), model_id,
        │       model_name, generated_at, endpoint}. Pulled directly from
        │       ds_model_registry-backed fields every endpoint already returns.
        │
        ├─► LLM composes a natural-language answer using ONLY the retrieved
        │       tool payloads as context (no free-generation of numbers).
        │
        └─► Verification pass (deterministic, code, not the LLM): every
                number/claim in the drafted answer is extracted and checked
                against the actual tool-result payloads. Anything that
                doesn't trace to a retrieved value is stripped or the
                answer is downgraded to "low confidence" before it is
                ever shown to the user.
        ▼
Answer + a structured, code-assembled "Sources" panel (tables, model
versions, generated_at) — never LLM-authored citation text.
```

Nothing in this design requires a new database role, a new write path, or a new trust boundary. The copilot is a new *client* of the existing `atlas_reporting`-backed API surface — architecturally, it is closer to "a second frontend" than to "a second analytics engine," which is exactly the line the request draws and the line this design is built to hold.

## 3. Retrieval strategy — tool-calling over existing endpoints, not SQL generation

**Explicitly rejected as a retrieval strategy: SQL generation**, even constrained/templated SQL generation. Every existing dashboard endpoint already encodes real business logic beyond a raw `SELECT` — role gating, ETL-run-keyed caching (`app/api/cache.py`), null-handling for structurally-unavailable metrics (e.g., `on_time_delivery_rate`'s disclosed unavailability), and pagination. Regenerating that logic in LLM-authored SQL would mean either duplicating it (a maintenance liability — two places that must agree on what "current" means) or omitting it (silently wrong answers, e.g., a generated query that misses the disclosed `on_time_delivery_rate` caveat). Calling the existing endpoint gets that logic for free and guarantees the copilot can never say something the dashboards themselves wouldn't say.

**Tool set** (illustrative, one tool per existing endpoint, no new endpoints required for the retrieval capabilities below):

| Capability requested | Existing endpoint(s) it maps to | New backend work needed |
|---|---|---|
| KPI explanation | `/executive`, `/sales`, `/inventory`, `/procurement`, `/supplier`, `/operational` summaries | None — direct call |
| Forecast explanation | `/planning/forecast/summary`, `/detail`, `/experiments` | None |
| Supplier risk explanation | `/planning/supplier-risk/detail` — already returns `triggering_metrics` | None |
| Inventory recommendation explanation | `/planning/inventory-policy/detail` — already returns `contributing_factors` + `business_rationale` | None |
| Service-level (stockout/backorder) explanation | `/planning/service-level/detail` — already returns `*_contributing_factors` | None |
| Scenario comparison | `/planning/scenarios/compare` — built for exactly this in Module E | None |
| Dashboard summarization | Templated aggregation across summary endpoints | Orchestration only |
| "Anomaly" explanation | `/service-level/detail` (high stockout probability), `/supplier-risk/detail` (High classification) | **Scope correction, below** |
| Executive briefing generation | Templated synthesis across multiple summary endpoints | Orchestration + heaviest verification burden |

**Scope correction on "anomaly explanation":** ATLAS has no dedicated anomaly-detection module (the prior review classified that as research-only/marginal, substantially covered by Modules C/D/E already). The copilot must **explain existing flags** Module D/C already computed (a high stockout probability, a High risk classification) — it must not be asked, and must not attempt, to detect new anomalies itself. This is worth stating explicitly in the tool contract, not left implicit, because "anomaly explanation" reads as a detection capability and it is not one here.

**Executive briefing generation is explicitly out of scope for the initial release**, per authorization — not deferred as "build it last" but excluded from this phase entirely. It synthesizes across the most sources at once, which is where verification is hardest and where drift between "what the answer says" and "what the data says" is most likely; excluding it keeps the initial verification harness (§5, and the full specification in `docs/phase8-grounding-spec.md`) scoped to capabilities that are actually tractable to verify with the claims-list approach. Revisiting it is a decision for a later phase, after the initial-scope harness has run against real usage — not a milestone inside this one.

**Approved initial scope, stated exhaustively**: natural-language warehouse queries, KPI explanation, forecast explanation, supplier risk explanation, inventory recommendation explanation, scenario comparison, and explanation of existing risk/stockout flags already computed by Modules C/D ("anomaly explanation," scope-corrected per the row above). Nothing beyond this list is in scope for the initial release.

## 4. Grounding and citation framework

The request's grounding requirement — every answer must include source tables, source metrics, calculation references, versions, and confidence — is treated here as a **code contract, not a prompting instruction.** An LLM told "always cite your sources" will comply most of the time and drift the rest of the time; "most of the time" is not an acceptable bar for a platform whose entire differentiator is that every other module's output is provably correct.

The enforcement mechanism:

1. Every tool wrapper returns `(payload, citation)` as a pair — the citation is built by the orchestrator from fields the endpoint already returns (`model_id`, `model_name`, `generated_at`, `source_*_model_id` chains that already exist on Module B/D/E rows), never by the LLM.
2. The LLM is prompted to answer using only retrieved payload values, and to tag which retrieved fact backs each claim.
3. A deterministic post-processor extracts every number in the drafted answer and checks it against the union of retrieved payloads (numeric match within a small tolerance for rounding). Any unmatched number is either removed or causes the whole answer to be downgraded to "low confidence, could not verify" rather than shown as a confident claim.
4. The "Sources" panel shown to the user is assembled entirely from step 1's citation objects — structured data, rendered by the frontend, never LLM-authored prose pretending to be a citation.

This is the single most load-bearing part of the design. It is also the part most likely to be under-built if this is rushed — "add an LLM that cites its sources" is an easy sentence to write and a nontrivial system to get right.

## 5. Evaluation framework (the gating deliverable — full spec in `docs/phase8-grounding-spec.md`)

Every other module in ATLAS earned its place through real, computed validation evidence, not an assertion of correctness: MAPE against a baseline (A), Brier score against a baseline (D), correlation checks (C), walk-forward achieved service level (B), deterministic-replay to 10 decimal places (E), a live-checked empirical premise (F's transit-time invariance). The copilot must be held to the same standard before it ships, or it is the one module in the platform whose correctness is merely claimed.

Per authorization, this is no longer a precondition to sequence before implementation — it **is** the first implementation deliverable and a mandatory CI-blocking check. Summary (full design, including the claims-list verification architecture, CI thresholds, and failure handling, is specified in `docs/phase8-grounding-spec.md`):

- **A fixed eval set of Q&A pairs with known-correct grounded answers**, one or more per approved-scope capability, each independently verifiable against real `ds_model_registry`-backed fields.
- **Citation-traceability at 100%, enforced by construction** — every rendered number traces to a verified claim, or it is dropped before the answer is ever shown, not merely measured and reported.
- **A negative and adversarial eval set** — questions the copilot should refuse (structurally unanswerable, out-of-scope, or nonexistent entities) and false-premise/hallucination-provoking questions. Correct behavior is a structured refusal, not a confident fabrication — this is the metric that matters most for "grounded," not raw helpfulness.
- **CI-blocking thresholds** on all of the above — the build fails if grounding accuracy falls below the approved threshold, and the chat interface may not merge while any threshold is failing.

Until this harness exists and passes against the eval sets in `docs/phase8-grounding-spec.md` §5–6, "grounded" is a design intention, not a proven property — which is why implementation of the harness itself still requires a separate go-ahead beyond this document, and why the chat interface specifically may not begin until the harness is green.

## 6. Security model

No new trust boundary is created. The copilot:

- Receives the same `X-Atlas-Role` header as every dashboard request and passes it straight through to the same `require_role(...)` dependency every endpoint already enforces — a user cannot get the copilot to retrieve anything their role couldn't already see via the dashboard.
- Holds no database credential of its own — it has no ability to query `atlas_olap` or `atlas_oltp` directly, by construction, not by policy. Removing this capability is a matter of never writing the code path, not remembering to restrict one.
- Cannot invoke a write operation because none exist for it to call — every endpoint in the tool set is one of the platform's existing `GET`-only routes; there is no `POST`/`PUT`/`DELETE` route anywhere in `main.py` for a compromised or misdirected tool call to reach.
- Sends only already-role-authorized data to the external LLM API as context — nothing the user couldn't already see. (If the LLM provider is external, this is worth flagging as a data-handling consideration for a real deployment, separate from the in-platform security model: portfolio/demo use is a materially different data-sharing calculus than a real company's supplier and cost data.)

This is a strong section, and the main practical action to preserve it is discipline: the tool set must stay a fixed allowlist of existing read routes, never grow to include a raw-query escape hatch "just for one edge case."

## 7. Comparison against the other Phase 8 alternatives

| Alternative | Where it sits relative to the deterministic core | Verdict recap |
|---|---|---|
| ML forecasting models | **Inside** — replaces a validated prediction | Reject |
| Probabilistic inventory optimization | **Inside** — replaces a validated formula | Research only |
| Bayesian demand uncertainty | **Inside** — replaces validated shrinkage logic | Reject |
| Reinforcement learning inventory policies | **Inside** — replaces a validated, auditable policy | Reject |
| Graph-based routing optimization | **Inside**, and targets data that doesn't support it | Reject |
| Automated anomaly detection | **Inside**, marginal overlap with existing coverage | Research only |
| **Grounded analytics copilot (this proposal)** | **Downstream** — consumes already-validated outputs, produces no new analytical conclusion | **Approved, verification-first** |

This is the structural argument for treating the copilot differently from every other Phase 8 candidate reviewed so far: every other alternative proposes to change *what gets computed*, which is precisely the part of ATLAS this project has spent six modules proving correct. A retrieval-only copilot, held to the verification standard in §5, cannot corrupt that layer even in principle — its entire failure mode is *misdescribing* an already-correct answer, not computing a wrong one. That is a smaller, more containable risk category, which is why this is the first "AI-flavored" proposal across two review rounds to earn anything better than reject.

It is not, however, risk-free, and it should not be waved through on the strength of that structural argument alone — see §8.

## 8. Evaluation against the eight review axes

| Axis | Assessment |
|---|---|
| **Architectural fit** | Strong, if the "existing-endpoint-only" constraint holds. It adds a new *consumer* of the existing API surface, not a new analytical layer — the one AI-adjacent proposal that doesn't ask the platform's deterministic core to bend around it. |
| **Security** | Strong, per §6 — no new credential, no new write surface, inherits the existing role gate exactly. |
| **Maintainability** | Real, non-trivial addition — a tool router, a citation-verification layer, and an eval harness are all new code the other six modules don't need. This is a genuinely new kind of component for this codebase, not a seventh instance of the existing module pattern. |
| **Grounding** | Achievable, but only with the code-enforced verification in §4 — a prompted-only version would not meet this bar and should not be described as "grounded." |
| **Hallucination risk** | The central risk. Materially reduced (not eliminated) by tool-calling over a fixed, safe endpoint set plus deterministic answer-verification — but any LLM-authored prose still carries residual risk of misstatement, emphasis error, or conflating two retrieved facts, which is why §5's eval harness is a precondition, not a nice-to-have. |
| **Explainability** | Potentially additive to the platform's strongest existing property — if (and only if) citations are code-assembled from real `ds_model_registry`-backed fields as designed, this extends "every recommendation carries its lineage" into a conversational surface rather than diluting it. |
| **Performance** | Real but bounded latency/cost overhead from an external LLM call per question; not a concern for a portfolio project's demo traffic, would need real budgeting for anything beyond that. |
| **Portfolio value** | Genuine, if built with the verification harness front and center of the story: "I built an LLM feature and also built the system that catches it when it's wrong" is a stronger, more current, and more differentiated signal than either "I avoided LLMs entirely" or "I bolted on a chatbot." Built without that harness, it becomes exactly the buzzword-chasing risk the original review warned against. |

## 9. Implementation roadmap (approved ordering — implementation not yet authorized to begin)

1. **Verification harness (mandatory first deliverable, CI-blocking gate):** build the tool router over the existing read endpoints, the code-enforced claims/citation/verification layer, and the full eval harness per `docs/phase8-grounding-spec.md` — every threshold in that spec's §6 passing. No user-facing surface yet. This is not a prerequisite task sequenced before "real" work; it *is* the first real work, and it stays wired into CI permanently after this point, gating every subsequent change, not just the initial merge.
2. **Tool layer:** the fixed, typed tool set wrapping approved-scope endpoints only (§3's table, excluding executive briefing generation entirely). Exercised and proven against the harness from step 1 before any chat surface exists.
3. **Chat interface:** a read-only chat panel added to the dashboard frontend, single-turn Q&A, scoped exactly to the approved initial scope. **May not be merged while the harness from step 1 is failing, on any subsequent change, permanently — not only at initial launch.**

Executive briefing generation and multi-turn conversational context are explicitly not part of this roadmap — any future consideration of either is a separate proposal, evaluated on its own evidence, not an automatic next step after step 3.

## 10. Final confirming review — distinctness from previously rejected Phase 8 proposals

Restated directly, as required before any implementation code is written: this copilot is approved because it satisfies a test none of the previously rejected proposals do — it **preserves the deterministic, validated core of ATLAS and extends it through grounded explanation, not new computation.**

| Test | ML forecasting / Bayesian / RL / graph routing | This copilot |
|---|---|---|
| Can it change what a module computes? | Yes — that's the proposal | No — structurally cannot; it has no write path and no analytical authority, only retrieval |
| Does it require new data the platform doesn't already validate? | Sometimes (e.g., EOQ's cost inputs) | No — consumes only already-validated, already-persisted outputs |
| Is its correctness provable with the same evidence discipline as the rest of the platform? | Yes, and each was held to that bar (which is why several were rejected on the evidence) | Yes, held to the same bar via `docs/phase8-grounding-spec.md` — not exempted from it |
| Does its failure mode corrupt a downstream decision, or just a description of one? | Corrupts the decision itself | Only ever misdescribes an already-correct decision, and even that is the specific thing the verification harness exists to catch |

This is not a reason to relax scrutiny — §5–8 exist precisely because "it can only misdescribe, not miscompute" is a smaller risk category, not a zero one. It is the reason this proposal earned a different disposition than every other AI-adjacent idea evaluated across both review rounds.

## 11. Final recommendation

**Approved, verification-first.** Implementation of the harness specified in `docs/phase8-grounding-spec.md` is authorized as the next deliverable pending your explicit go-ahead beyond this document; the chat interface remains blocked until that harness is built and green, permanently, not just at launch. This is the first AI-adjacent Phase 8 proposal across two review rounds to survive serious scrutiny, because it is structurally incapable of corrupting the deterministic core the rest of ATLAS was built to protect. It earned "approved," not "implement now" outright, because the hardest and most important part of this design — proving the grounding claim rather than asserting it — does not exist yet, and building the visible, demo-able part before the invisible, load-bearing part would produce a tool that looks like it fits this platform's standards without actually meeting them.
